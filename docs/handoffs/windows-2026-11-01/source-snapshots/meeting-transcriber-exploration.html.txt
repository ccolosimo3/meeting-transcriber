<h1>Meeting Transcriber improvement and replacement options</h1>
<p class="lead">Given your disappointing earlier local-model results and priority on room speaker separation, retain AssemblyAI as the baseline and improve the reading and retrieval workflow first. Treat Vibe and other local replacements as candidates for a controlled quality comparison, not established quality equivalents.</p>
<p>The decision is whether maintaining this personal meeting recorder buys enough control and convenience to justify development. The current app is a macOS room recorder with cloud transcription. It already has inexpensive processing, durable local files, and a useful agent handoff. Its largest visible gaps are discovering past meetings, checking transcript passages against audio, and using it outside a terminal.</p>

<h2 id="baseline">What the app already does well</h2>
<p>The checked-out source records a microphone to a local WAV file and uploads only when transcription is requested. AssemblyAI performs transcription and speaker separation. Canonical JSON supplies derived Markdown and HTML; speaker display names can be changed without replacing transcript content. Remote deletion is attempted after local publication, and an unconfirmed deletion has its own recovery state. These are useful owners to retain, not infrastructure a GUI needs to replace. See the <a href="https://github.com/ccolosimo3/meeting-transcriber/blob/76959539785b31da544eea6e6d08f217aedcf95c/docs/DEVELOPMENT.md">development architecture</a>.</p>
<p>The GitHub description still refers to MLX Whisper and pyannote. That is stale: <a href="https://github.com/ccolosimo3/meeting-transcriber/commit/9adebf4fbac29edf79cc26d766e171e87ad4021c">the August consolidation</a> deliberately removed those local inference paths. The current production Python package has no third-party runtime dependencies. Fully offline transcription would reintroduce a substantial responsibility.</p>
<div class="callout"><strong>Running cost is already low.</strong> Published AssemblyAI pricing is $0.21 per audio hour for Universal-3.5 Pro plus $0.02 for speaker diarization. The app requests both, for approximately <strong>$0.23/hour</strong>: 10 hours/month ≈ $2.30, 20 hours ≈ $4.60, 40 hours ≈ $9.20. These estimates exclude taxes, account-specific terms, other services and any paid reprocessing. <a href="https://www.assemblyai.com/pricing">AssemblyAI pricing</a>.</div>
<p>You confirmed that most meetings are in-person room meetings. That prioritizes microphone placement, multi-person speaker separation, and checking text against saved audio; system-audio capture is secondary. Windows urgency, meeting volume, budget and whether work policy permits cloud processing remain unspecified. Those facts can change the ordering below.</p>

<h3>Quality follow-up from repository history</h3>
<p>Your original implementation used MLX Whisper large-v3-turbo plus pyannote Community-1 through WhisperX. Its documentation records a 114.5-second comparison of Small, Turbo and Distil Large V3 on CPU and MLX; Turbo was selected, with a reported 6.96-second mean processing time. This is a short local-model comparison, not a long-meeting speaker-quality benchmark against AssemblyAI. <a href="https://github.com/ccolosimo3/meeting-transcriber/blob/7a5922f/docs/DEVELOPMENT.md">Original development notes</a>.</p>
<p>The old adapter assigned each phrase to its overlap-majority speaker while retaining word-level labels as metadata. A phrase spanning a speaker change could therefore appear under one person's name. That is a possible contributor to perceived attribution errors; the source alone cannot establish the cause of your observed problems. <a href="https://github.com/ccolosimo3/meeting-transcriber/blob/7a5922f/lib/transcribe_mlx.py">Original speaker assignment</a>.</p>
<p>Vibe v3.3.0, the latest release checked on October 31, configures NVIDIA's <code>diar_streaming_sortformer_4spk-v2</code>: a four-speaker diarization model. That is a material limitation for larger room meetings. Its development branch has switched to Nemotron-3-Diarization, whose upstream model supports eight speakers, but that does not establish the behavior of the released installer or accuracy parity with AssemblyAI. <a href="https://github.com/thewh1teagle/vibe/blob/v3.3.0/desktop/src/lib/config.ts">Release model configuration</a>, <a href="https://github.com/thewh1teagle/vibe/blob/da8c2ca53b6c7ff44f7a1314c3be862d466c3427/server/crates/vibe-server/src/server/diarization.rs">development implementation</a>, <a href="https://huggingface.co/nvidia/Nemotron-3-Diarization">upstream model</a>.</p>
<p>No controlled Vibe-versus-AssemblyAI room-meeting comparison was found in this bounded investigation. AssemblyAI publishes meeting diarization results, but these are vendor-run evaluations and do not directly score Vibe. They cannot establish a numerical quality gap between the two. <a href="https://www.assemblyai.com/benchmarks">Benchmark methodology and results</a>.</p>
<p>Granola is a different tradeoff: a Windows/Mac cloud notetaker with a free tier and a $14/user/month Business tier, but it does not retain playable meeting audio. That removes an important checking and archival capability your app already has. <a href="https://www.granola.ai/pricing">Pricing</a>, <a href="https://www.granola.ai/blog/local-first-ai-notetaker-vs-cloud">audio handling</a>. Existing Teams licensing may also help for online calls, but identifying several people sharing one room microphone has additional licensing/enrollment requirements; it is not established as a free substitute here. <a href="https://support.microsoft.com/en-us/accessibility/teams/common-issues-using-intelligent-speakers-in-microsoft-teams">Microsoft room recognition requirements</a>.</p>

<h2 id="architecture">Credible architecture choices</h2>
<div class="scroll"><table><thead><tr><th>Approach</th><th>Reuse, operations and cost</th><th>Correctness and reversibility</th><th>Disposition</th></tr></thead><tbody>
<tr><td>Adopt an existing app</td><td>Lowest code maintenance; local model setup and product upgrades replace your packaging work. <tr><td>Extend HTML + add a library</td><td>Maximum reuse of canonical JSON, renderers, names and discovery. Existing API costs remain low.</td><td>Mostly additive and easy to reverse. <tr><td>Cross-platform Python core + desktop UI</td><td>Retain provider/persistence logic; move required shell orchestration to a portable owner. Python/Tkinter is the smaller UI route; Electron/Tauri supports a richer web interface but adds packaging/toolchains.</td><td>Requires Windows capture, ACL, cancellation and process-lifecycle proof. Structured progress must not duplicate provider state or trigger automatic paid retries.</td><td>Appropriate only after choosing to maintain the app and settling room-only versus call capture.</td></tr>
</tbody></table></div>
<p>A full backend rewrite has no demonstrated advantage here. Existing code already separates provider lifecycle, canonical persistence, run discovery, identity and rendering. Recreating those contracts would increase regression risk without being necessary for a better interface.</p>
<p>For a small utility, a Python front door plus a simple window is the minimum plausible Windows route. For a polished web interface, keep the same Python worker behind a desktop shell. Electron officially supports Windows loopback capture; Tauri supports Python sidecars but does not itself prove the audio boundary. Choose a shell after capture needs are known. <a href="https://docs.python.org/3.13/library/tkinter.html">Tkinter</a>, <a href="https://www.electronjs.org/docs/latest/api/session#sessetdisplaymediarequesthandlerhandler-opts">Electron capture API</a>, <a href="https://v2.tauri.app/develop/sidecar/">Tauri sidecars</a>.</p>

<h2 id="proof">What would change the recommendation</h2>
<ul>
<li><strong>Work data must remain offline:</strong> favor a local replacement first. The current AssemblyAI path is not offline, regardless of local recording or later deletion.</li>
<li><strong>Windows is required now:</strong> test an existing Windows app before building. If keeping custom software, prove the capture/privacy boundary before writing the GUI.</li>
<li><strong>Most meetings are calls:</strong> simultaneous microphone and output audio becomes essential. A room microphone port does not establish this capability.</li>
<li><strong>The PC cannot run accurate local models quickly:</strong> the current low-cost cloud backend may offer a better experience than a free local app.</li>
<li><strong>Custom portable artifacts and agent handoff are central:</strong> incremental improvements retain their exact semantics, while third-party export behavior needs checking.</li>
</ul>
<h3>A bounded replacement trial</h3>
<p>Use the same permitted, representative 10–15 minute room sample with several speakers, a few names/numbers, some overlap and quiet passages. In Vibe and SpeechPulse, compare correction time, speaker consistency, processing time, audio seeking, exported timestamps/names, and how quickly the meeting can be found again. Compare microphone placement before attributing distant or muffled speech to the software. If calls later become a requirement, separately record synthetic playback plus local speech while wearing headphones and verify both sides. Prefer the tool that reliably completes the actual workflow; feature checklists do not establish this.</p>
<h3>The smallest Windows proof if development is selected</h3>
<ol>
<li>Capture a short microphone sample via Windows DirectShow, stop gracefully, validate with FFprobe, and finalize the existing partial-to-complete WAV flow. <a href="https://ffmpeg.org/ffmpeg-devices.html#dshow">FFmpeg DirectShow</a>.</li>
<li>If calls matter, separately prove microphone + WASAPI output loopback capture, synchronization and absence of duplicated audio. Do not rely on optional hardware Stereo Mix. <a href="https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording">Microsoft loopback documentation</a>.</li>
<li>Publish a synthetic transcript through the existing persistence owner under private Windows ACLs, including temporary files and atomic replacement; exercise provider lifecycle against a loopback stub. Python 3.13 supports <code>fchmod</code> on Windows, but <code>chmod</code> does not establish POSIX-style privacy there. <a href="https://docs.python.org/3.13/library/os.html#os.chmod">Python permissions</a>.</li>
</ol>
<p>These prove narrow mechanisms. They do not establish long meetings, device switching, Bluetooth behavior, sleep recovery, installer signing or macOS regression freedom. A subsequent implementation plan should include only the checks warranted by its selected boundary.</p>
